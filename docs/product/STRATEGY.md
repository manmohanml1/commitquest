# Product strategy and return loop

## Positioning

CommitQuest is an evidence-backed engineering progression product presented as an evolving RPG world.

The map, citadels, quests, encounters, chapters, and unlocks are the interaction language. The lasting value is that a developer can understand what a repository demonstrates, see how real engineering outcomes changed it, identify a useful next improvement, and share the supporting evidence.

CommitQuest never equates activity volume with engineering quality and never claims that GitHub endorses or certifies its interpretation. Product language uses **GitHub-sourced evidence** or **verified from GitHub evidence**.

## Primary v1 user

The v1 product serves an individual developer, student, portfolio builder, or open-source contributor who wants to improve and demonstrate one real repository. Maintainer onboarding is a secondary experiment. Cross-repository profiles, organizations, team competition, and paid administration remain later products.

## Return loop

```text
preview or connect a repository
  -> establish an evidence-backed campaign baseline
  -> complete normal engineering work on GitHub
  -> ingest and deduplicate the resulting evidence
  -> update campaign state and explain the outcome
  -> suggest one concrete applicable improvement quest
  -> unlock an evidence-linked presentation change
  -> return after the next meaningful outcome
```

Version 0.3 proves translation. Versions 0.4–0.6 create ownership and return. Version 0.7 creates explainable progression. Version 0.8 makes the result safely shareable. Versions 0.9–1.0 prove the system is fair, accessible, secure, recoverable, and operable.

Version 0.5 also replaces the authenticated v0.4 presentation with one shared application shell and two complete visual modes: a focused Modern workspace and an original medieval-fantasy Chronicle. They share the same evidence, routes, security boundaries, and component semantics; the mode changes presentation, never campaign truth.

## Progression principles

- Reward outcomes such as a resolved issue, merged and reviewed change, automated check, security control, recovery improvement, or traceable release.
- Do not reward commit count, lines changed, comments, time online, or repetitive cosmetic activity.
- Apply only dimensions relevant to the repository type.
- Link every award and unlock to its evidence and ruleset version.
- Use repository-authored and inferred evidence for recommendations unless a stronger evidence level justifies progression.
- Preserve historical rewards with the ruleset that created them.
- Make missing, unavailable, private, not applicable, and unknown visibly different.

## AI boundary

AI is downstream of deterministic evidence. It may later rewrite an explanation for clarity, group existing recommendations, or help a user explore evidence. It cannot create achievements, change scores, mutate campaign state, or substitute unsupported claims for missing data. Every AI-assisted surface has a deterministic fallback.

## Post-1.0 options

1. Cross-repository engineering mastery and public developer profiles.
2. Open-source onboarding paths that classify contribution areas and scoped issues.
3. A GitHub Action that generates a static campaign artifact for GitHub Pages.
4. Team views only after explicit research into surveillance, incentive, and fairness risks.

The first option is the preferred product expansion. The static Action is the preferred zero-infrastructure companion. Team delivery gamification is not the default business direction.
